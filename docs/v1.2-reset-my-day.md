# Hemera v1.2 — Reset My Day (product + technical spec)

**Status:** approved (user, post-MVP) — D21–D27 confirmed 2026-10-22.
X1–X3 implemented; X4 device verification pending. Builds on the closed
MVP (v0.1.0) and v1.1 (Reminders, R4 device pass pending).

Sources: product brief §10 (post-MVP queue); requirements §8 (Reset My
Day excluded from MVP) and §9 (deferred feature specification); §2.1
rules T4/T6; D3 (the 7-day archive threshold).

## 1. Scope

**In:** one review screen that batches the handling of tasks carried
over from earlier days, and a quiet entry point for it on Today.

**Out of v1.2:** completed items on the review screen, missed habit
occurrences on the review screen, overdue-deadline-only tasks on the
review screen, scheduling a carried-over task for a day other than
today, undo after the toast is gone, per-task snooze, export/backup,
dark mode, widgets, any network use (`INTERNET` stays blocked).

## 2. Decisions (D21–D27)

| # | Decision |
| --- | --- |
| D21 | **The trigger is a quiet line on Today.** When Today is showing and at least one task is carried over, a single caption line sits under the Today pill: "N tasks are still waiting." Tapping it opens the review. No takeover, no modal, no badge, no automatic navigation, no count of anything else. |
| D22 | **The review covers exactly the carried-over tasks**: open, timed, scheduled on an earlier day, and inside D3's 7-day window. A task that is merely late *today* is not carried over and is not offered — it already has a one-tap action in Today's "Needs rescheduling" section. Tasks older than 7 days belong to the muted *Later* group and are not offered either. |
| D23 | **Every row starts on "Keep time."** An untouched row keeps its clock time, today. Untouched rows therefore follow the default on Confirm — the review is a place to adjust a few rows, not to re-decide all of them. |
| D24 | **Keep time keeps the clock time even when it has already passed today.** Nothing is silently rolled forward to tomorrow and no free slot is hunted for. The task lands on today's timeline at that time and still reads as overdue until it is moved. |
| D25 | **The review shows overdue scheduled tasks and nothing else.** Requirements §9 permitted a preserved-completed section and missed habit occurrences; neither is built. The Habits tab already shows missed days neutrally (H2), and a completed list next to a carried-over list reads like a scoreboard. |
| D26 | **One transaction, one undo.** Confirm applies every row's choice in a single database transaction, and the history record is written in that same transaction — either everything happened or nothing did. The result is announced in a toast with a single Undo that restores the previous schedule of every task the reset changed. |
| D27 | **Groups are factual.** Rows are grouped by how late they are — "Yesterday" and "Earlier" (the 7-day window caps the range) — and each row states the exact date and time it was scheduled for. No totals, no percentages, no streaks, no failure language (brief §7, H4). |

## 3. Functional requirements

**FR-X1 — The quiet line on Today.**

- AC: With no carried-over task, the line is absent.
- AC: With N carried-over tasks, the line reads "N tasks are still
  waiting." ("1 task is still waiting." for a single task).
- AC: The line's accessibility label is "Review N tasks that are still
  waiting".
- AC: The line never appears when a day other than today is being
  viewed.
- AC: The line is a statement of pending work, not a nag: it makes no
  claim about how the user spent yesterday, and it disappears as soon as
  nothing is carried over.

**FR-X2 — The review screen.** A dedicated screen titled "Reset my day"
lists every carried-over task, grouped by how late it is, each row
offering four choices.

- AC: The screen lists exactly the carried-over tasks (D22).
- AC: Groups appear in the order *Yesterday* → *Earlier*; within a
  group, rows are ordered by their scheduled start time, earliest
  first.
- AC: Every row shows the task title and "was scheduled &lt;weekday&gt;
  &lt;day&gt; &lt;month&gt;, &lt;time&gt;" — the exact date, not only the
  weekday, because a row in *Earlier* can be up to seven days old
  (D27).
- AC: Every row offers exactly four choices: *Keep time*, *Move to
  pool*, *Pick new time*, *Dismiss*.
- AC: Every row starts on *Keep time* (D23).
- AC: The screen contains nothing else (D25).
- AC: With nothing carried over the screen shows an empty state
  ("Nothing is waiting.") and a way back.

**FR-X3 — The four choices.**

- AC: *Keep time* moves the task to today at the same clock time and
  keeps its duration.
- AC: *Move to pool* clears the schedule entirely (date, time and
  duration) and the task returns to the plain unscheduled pool.
- AC: *Pick new time* opens the native time picker; the picked time
  schedules the task for today, keeping its duration. The chip then
  reads "Pick HH:mm" so the choice is visible without opening the
  picker again.
- AC: *Dismiss* leaves the task exactly as it is — it keeps its original
  past date and keeps deriving "needs rescheduling".
- AC: *Keep time* keeps a clock time that has already passed today
  (D24).

**FR-X4 — Confirm applies everything at once.**

- AC: Confirm applies every row's choice in a single database
  transaction; if any write fails, no task is changed.
- AC: The same transaction records what happened (FR-X5).
- AC: After Confirm the review closes and Today shows the result.
- AC: The result is announced in a toast: "N tasks updated" with an
  *Undo* action. When nothing changed, the toast reads "Nothing
  changed." and offers no Undo.
- AC: *Undo* restores the previous date, time and duration of every task
  the reset changed, and removes the reset record. It is available for
  as long as the toast is on screen.

**FR-X5 — History.** Each applied reset is recorded: the local day it
was applied to, when it was applied, and for every task the choice
made plus the schedule before and after.

- AC: The record is written in the same transaction as the task updates
  (D26).
- AC: The record is removed when the reset is undone.
- AC: No History screen is built — that stays out of scope. The record
  exists so that what happened is never lost, and so that Undo can be
  driven from the database rather than from memory.

**FR-X6 — Reminders follow.** A task moved to today by the reset gets
its reminder at its new start time; a task moved to the pool loses its
reminder.

- AC: After a reset, the installed notification set matches the new
  schedules — no reminder for a pooled task, one reminder for a task
  scheduled today.
- AC: A failed reminder sync never blocks the reset; reminders are
  decoration on data that is already committed.

**FR-X7 — Tone.** The screen and the line use calm, factual wording:
"N tasks are still waiting.", "was scheduled Tue 09:00", "Nothing
changed." No completion counts, no totals, no percentages, no streaks,
no failure language (brief §7, H4).

## 4. Technical design

### 4.1 Data model (migration 002)

```sql
CREATE TABLE IF NOT EXISTS day_resets (
  id          TEXT PRIMARY KEY,
  date        TEXT NOT NULL,
  applied_at  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS day_reset_items (
  reset_id       TEXT NOT NULL REFERENCES day_resets (id) ON DELETE CASCADE,
  task_id        TEXT NOT NULL,
  action         TEXT NOT NULL
                  CHECK (action IN ('keep','pool','pick','dismiss')),
  from_date      TEXT,
  from_time      TEXT,
  from_duration  INTEGER,
  to_date        TEXT,
  to_time        TEXT,
  to_duration    INTEGER,
  PRIMARY KEY (reset_id, task_id)
);
```

The before-image lives in the history, so Undo restores from the
database and survives the process being killed. `PRAGMA foreign_keys =
ON` is already set when the database is opened (`src/db/open.ts`), so
the cascade works. Migration 002 is additive; `001_initial` is
untouched.

### 4.2 Modules (mirroring the existing layering)

- `src/domain/reset.ts` — **pure** and unit-tested: `resetCandidates`,
  `groupResetCandidates`, `defaultChoice`, `planReset`.
- `src/repositories/resets.ts` — `apply(entries, dateKey)` writes the
  task updates and the history rows in one transaction; `undo(resetId)`
  restores the before-image and deletes the record.
- `src/stores/resetStore.ts` — `apply` / `undo`; patches the tasks store
  and re-syncs reminders (deferred import, as in the tasks store).
- `src/services.ts` — a `resets` repository is added to the service
  container and wired in `src/bootstrap.ts`.
- `app/reset.tsx` — the review screen.
- `app/(tabs)/index.tsx` — the quiet line (FR-X1).
- `app/_layout.tsx` — a `reset` route (card presentation, its own
  header title).

### 4.3 The pure model

- A **candidate** is an open task with a start time, scheduled on a day
  before today, whose scheduled block ended within the last 7 days
  (D22). `taskPoolSection(task, now) === 'reschedule'` already encodes
  the 7-day window, so the candidate rule reuses it rather than
  restating D3.
- **Lateness** is counted in calendar days between the scheduled date
  and today — 1 → *Yesterday*, 2–7 → *Earlier*.
- A **choice** is `{ action, time? }`; the default is
  `{ action: 'keep' }`.
- `planReset` turns candidates + choices into a list of entries, each
  with the schedule *before* and the schedule *after*. *Dismiss* yields
  an entry whose before and after are equal, which the repository
  records but does not write.

### 4.4 Apply and undo

`resets.apply` opens one transaction: insert the `day_resets` row,
update each changed task, insert each `day_reset_items` row. A failure
rolls the whole thing back, so a reset is never half-applied.

`resets.undo` opens one transaction: restore every recorded
before-image, then delete the items and the reset row.

### 4.5 Failure behaviour

A failed apply is a `withWriteError`-style toast; the review stays
open and nothing is changed. A failed undo is the same. A failed
reminder sync is silent — it never blocks a reset.

### 5.1 X4 device script

**Build under test.** `eas build -p android --profile preview` —
internal distribution APK, arm64-only, `NODE_ENV=production` (JS
bundled, so the app runs without Metro). Install it **over** the
previous preview build (same package `com.hemera.app`, `versionCode` 2)
so the upgrade path is covered too.

**Setup.** The review only ever offers tasks that were carried over, so
the pass needs a carried-over task. Create three tasks first:

| Task | Scheduled for | Start | Duration |
| --- | --- | --- | --- |
| T1 | tomorrow | 09:00 | 30 min |
| T2 | tomorrow | 14:00 | 45 min |
| T3 | the day after tomorrow | 08:00 | 30 min |

Then move the device clock forward (Settings → System → Date & time →
set time manually). Hemera refreshes "now" when it comes to the
foreground and every 60 s, so bring the app forward after each change.
Waiting two real days works too, and is the slower, honest version of
the same check.

| # | Step | Expected |
| --- | --- | --- |
| 1 | Fresh install → Today | No quiet line: nothing has been carried over (FR-X1). Today behaves exactly as it did in v1.1. |
| 2 | Schedule T1, T2 and T3 as above | Each task appears on its own day in the timeline. |
| 3 | Set the clock to tomorrow, 10:00; bring Hemera forward | T1 and T2 are late *today* and stay in "Needs rescheduling" — the quiet line is still absent (D22: late-today is not carried over). |
| 4 | Set the clock to the day after, 10:00; bring Hemera forward | The quiet line reads "2 tasks are still waiting." (T1, T2). T3 is scheduled later today, so it is not offered. |
| 5 | Tap the quiet line | The review opens, titled "Reset my day" (FR-X2). |
| 6 | Read the review | One group, "Yesterday", with two rows: each shows its title and "was scheduled Wed 21 Oct, 09:00" — the exact date, not only the weekday (D27). No completed tasks, no habits, no deadline-only tasks, nothing else on the screen (D25). No "Earlier" group yet — a group appears only when it has rows. |
| 7 | Look at the rows | Every row starts on "Keep &lt;its time&gt;", selected (D23). |
| 8 | Leave T1 on "Keep 09:00"; press "Move to pool" on T2 | The chips switch. |
| 9 | Press Confirm | The review closes. T1 is scheduled **today at 09:00** — the time that has already passed is not rolled forward (D24) — and T2 is in the plain unscheduled pool. The toast reads "1 task updated" with *Undo* (FR-X4). |
| 10 | Press *Undo* | T1 is back on yesterday at 09:00 and T2 is back on yesterday at 14:00. The quiet line reads "2 tasks are still waiting." again (FR-X4). |
| 11 | Set the clock forward two more days; reopen the review | Both groups are present: "Yesterday" (T3) and "Earlier" (T1, T2), in that order, each row stating its own date and time (D27). |
| 12 | On T1 press "Pick new time" and choose 18:30 | The chip reads "Pick 18:30" (FR-X3). |
| 13 | On T2 press "Dismiss", then Confirm | T2 keeps its original past date and still derives "needs rescheduling" — it returns in the next review (§6.2). The toast reads "2 tasks updated". |
| 14 | Set the clock forward eight more days | The quiet line is gone: tasks older than the 7-day window are no longer offered (D22, D3). |
| 15 | Browse back to a past day | The quiet line is absent — it belongs to Today only (FR-X1). |
| 16 | Read every string in the review and on the line | Factual wording only: no count of missed days, no "you failed", no streak, no guilt (brief §8, D25). |

**Notes.**

- The quiet line is the only entry point. There is no menu item, no
  badge, and no automatic takeover — that is the point of D21, so if a
  review ever opens by itself, that is a defect.
- A task that is *dismissed* keeps coming back until its date falls out
  of the 7-day window. That is deliberate, not a bug (§6.2).

## 6. Assumptions and risks

**6.1 Assumptions**

| # | Assumption | Materiality |
| --- | --- | --- |
| A18 | A carried-over task is one scheduled on an earlier *day*. A task that is late today stays in Today's "Needs rescheduling" section, where it already has a one-tap action. | Medium — reversible; widening the candidate rule is a one-line change in `resetCandidates`. |
| A19 | Within a group, rows are ordered by scheduled start time, earliest first — the review reads in the order the day was planned. | Low |
| A20 | The review screen is a card route, not a modal sheet: it is a multi-row review, not a quick pick. | Low |
| A21 | The history is written but never surfaced yet. No History UI is built (requirements §8 keeps History out of scope). | Low |

**6.2 Accepted limitations**

- Undo only lives as long as the toast. After it disappears the reset
  stands — the history is still on disk, but there is no surface to
  undo from.
- A task that is *dismissed* keeps deriving "needs rescheduling", so it
  comes back in the next review and the quiet line stays. That is
  deliberate: dismissing is a decision to leave it alone, not to
  forget it.
- *Pick new time* schedules for today only. Moving a task to another
  day is done in the task sheet, not here.
